# 二次开发改动记录

本文只记录我在原始开源方案基础上的真实增量，用于说明当前仓库中哪些能力是后续二次开发与工程化扩展的结果。

## 1. 病害标签扩展与标签映射

- **背景**：原始识别结果更偏向模型输出，业务侧很难直接把标签与病害知识库、方案库做稳定关联。
- **实现方式**：
  - 在 Flask 推理链路中按作物类型维护标签集合，保证模型输出标签与训练集语义保持一致。
  - 在 Spring Boot 侧补充 `DiseaseMapperService`，把 YOLO 标签映射到病害知识库中的 `diseaseId`。
  - 对图片识别结果增加标签解析逻辑，兼容单标签和 JSON 数组标签。
- **带来效果**：识别结果不再只是“框选 + 标签”，而是能够继续联动到病害知识、方案推荐和任务流程。

## 2. Spark LLM 集成

- **背景**：项目最初更偏识别与记录，缺少对自然语言咨询和智能解释的扩展能力。
- **实现方式**：
  - 新增 `SparkLlmService` / `SparkLlmServiceImpl`，封装讯飞星火 WebSocket 调用。
  - 补充 `LlmConfig` 与 `ChatController`，形成统一的后端接入入口。
  - 保留未配置或鉴权失败时的降级逻辑，避免本地演示环境完全不可用。
- **带来效果**：系统可以在识别与知识库结果之外，补充自然语言交互与智能问答能力。

## 3. Prompt 设计与降级回复策略

- **背景**：面向农业场景的问答，如果只依赖通用模型默认回复，表达往往不够贴近业务语境。
- **实现方式**：
  - 在聊天服务中增加面向病害、施药、天气、传感器等场景的应急回复模板。
  - 针对流式和非流式调用分别补充降级路径，保证接口在密钥缺失或鉴权失败时仍可演示。
  - 将农业场景常见问题的回答风格统一为“建议步骤 + 风险提醒”。
- **带来效果**：即使离线或第三方接口异常，项目仍能展示出完整的智能助手交互链路。

## 4. 智能方案生成与天气联动

- **背景**：病害识别本身不足以体现业务闭环，面试场景更需要展示“识别后如何决策”。
- **实现方式**：
  - 新增 `SolutionService` 相关逻辑，将病害知识、药剂信息、天气数据和传感器数据串联起来。
  - 通过 `/solution/generate` 生成结构化防治建议，包括剂量、风险提示、施药时间窗和限制条件。
  - 引入 Open-Meteo 天气缓存，减少重复请求并提升演示时的稳定性。
- **带来效果**：系统从“识别系统”升级为“识别 + 决策建议”的业务闭环平台。

## 5. 硬件控制与多端协同增强

- **背景**：原方案更多集中在视觉识别，缺少与设备执行链路的结合。
- **实现方式**：
  - 在后端增加 TCP 网关与设备控制接口，兼容既有 Android APP 的 Socket 协议。
  - 将传感器监测、识别记录、智能方案和设备控制放到同一套业务中台里管理。
  - 完善前后端与 Flask 三端联动文档，降低项目交接和演示成本。
- **带来效果**：仓库展示的不再只是单点 AI 能力，而是更完整的农业场景工程实践。

## 6. 文档与仓库整理

- **背景**：原始仓库更偏课程项目/实验项目风格，不利于直接作为公开作品展示。
- **实现方式**：
  - 统一 README、快速启动文档和后端/算法说明中的技术口径。
  - 清理公开仓库中的敏感配置，补充本地配置说明。
  - 将后端包名迁移为正式命名空间 `com.acunese.ljzp`，减少模板痕迹。
- **带来效果**：仓库更适合用于简历展示、面试交流和后续继续迭代。
